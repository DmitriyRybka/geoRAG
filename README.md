# Гео-RAG по центру Санкт-Петербурга

Система отвечает на вопросы о кафе, ресторанах и парках Центрального и Адмиралтейского районов и проверяет одну гипотезу.

**Гипотеза.** Обычный RAG (поиск по смыслу текста) ошибается на вопросах о расстояниях, а система с геоинструментом (расчёт по координатам) справляется лучше.

**Проверка.** Эталонные ответы вычисляет код по координатам. Их не размечают вручную, и их не оценивает LLM. Всё работает локально: Ollama (qwen2.5:3b), эмбеддинги `multilingual-e5-small` на CPU, платных API нет.

## Результат в двух словах

На 19 вопросах основной выборки (precision / recall, среднее по вопросам):

| Тип вопроса | N | Геосистема | RAG | Случайный выбор |
|---|---|---|---|---|
| в радиусе | 6 | 1.00 / 1.00 | 0.03 / 0.03 | 0.03 |
| ближайшие | 5 | 1.00 / 1.00 | 0.10 / 0.10 | 0.01 |
| по атрибуту | 4 | 1.00 / 1.00 | 0.36 / 0.36 | 0.02 |
| смешанные | 4 | 1.00 / 1.00 | 0.08 / 0.08 | 0.01 |

На вопросах с расстоянием RAG в среднем даёт 0.06 при случайном выборе мест нужной категории 0.02. Самое близкое место было в ответе у геосистемы в 7 случаях из 7, у RAG в 1 из 7. Размер ответа RAG равен размеру эталона, то есть ему подсказано, сколько мест нужно, поэтому разрыв оценён консервативно.

**Как читать эти числа.** 19 из 19 у геосистемы относятся к формулировкам, похожим на few-shot-примеры планировщика. На дополнительном наборе из 8 сложных формулировок она разобрала 6 из 8 (см. «Ограничения»). Гипотеза про расстояния подтверждена на этой выборке, но выборка маленькая, а доверительных интервалов нет. Подробности и примеры ошибок: [eval/results.md](eval/results.md), [eval/results_stress.md](eval/results_stress.md).

## Архитектура

```
вопрос ──► planner.py ──► landmarks.py ──► geo.py ──► ответ
          (qwen2.5:3b,    (resolve_place,  (радиус или   список мест
           Pydantic)       координаты из    k ближайших,  и расстояний
                           геокодинга)      метры, UTM)

вопрос ──► rag.py ──────────────────────────────────► top-k мест
          (описание из тегов OSM → e5-small → косинус)   (координат не знает)
```

| Файл | Что делает |
|---|---|
| `scripts/fetch_osm.py` | Скачивает кафе, рестораны и парки из OSM через OSMnx в `data/places.geojson` |
| `scripts/geocode_landmarks.py` | Координаты 7 ориентиров через геокодинг OSMnx в `data/landmarks.json` |
| `geo.py` | `places_within_radius`, `nearest_places`, `places_by_attribute`; расстояния в метрах |
| `planner.py` | Разбор вопроса в структуру `Plan` (категория, кухня, радиус, k, ориентир) через Ollama; сырой ответ модели хранится рядом с проверенным |
| `landmarks.py` | `resolve_place`: нечёткое сопоставление ориентиров (rapidfuzz), запасной поиск по тексту вопроса, смесь латиницы и кириллицы |
| `ask.py` | Вся цепочка для пользователя: `python ask.py "вопрос"` |
| `rag.py` | Базовая линия: описания мест, эмбеддинги, top-k |
| `eval/run_eval.py` | Эталоны, метрики, отчёты |
| `test_*.py` | Проверки модулей; `test_llm.py` это ранний эксперимент с планировщиком, оставлен как история |

## Как запустить

Нужны Python, [Ollama](https://ollama.com) и интернет для первой загрузки данных. Проверено только на Python 3.14, Windows 11, RTX 2050 (4 ГБ), 16 ГБ RAM; эмбеддинги считаются на CPU.

```bash
pip install -r requirements.txt
ollama pull qwen2.5:3b
python scripts/fetch_osm.py            # data/places.geojson, около 7 минут (Overpass бывает перегружен)
python scripts/geocode_landmarks.py    # data/landmarks.json
python ask.py "Найди кафе в 500 метрах от Летнего сада"
python rag.py "Найди кафе в 500 метрах от Летнего сада"
python eval/run_eval.py                # eval/results.md
```

`data/` и `cache/` не коммитятся: скрипты воспроизводят их. Модель `multilingual-e5-small` скачивается с Hugging Face при первом запуске `rag.py` (около 470 МБ). Данные OSM меняются, поэтому после повторной загрузки места и числа в отчёте могут немного отличаться.

Проверки модулей печатают результат (`test_geo.py` и `test_rag.py` завершаются ошибкой, если проверка не прошла). На Windows для кириллицы в консоли удобно `PYTHONUTF8=1`:

```bash
python test_geo.py && python test_resolve.py && python test_planner.py && python test_rag.py
```

## Ключевые решения

| Решение | Почему |
|---|---|
| Расстояния в EPSG:32636 (UTM 36N), в метрах | Градусы не равны метрам; в UTM Петербург (30,3° в.д.) искажён на доли процента. Сверено с гаверсинусом: 775,3 м против 773,4 м |
| Парки: расстояние до ближайшей точки полигона (`shapely.distance`), внутри парка 0 м | Вышло в одну строку, поэтому упрощение с центроидом не понадобилось |
| ID места `node/123`, `way/456`, `relation/789` | Стабильный ключ, по которому считаются precision и recall |
| Места без названия отброшены (217 из 2140) | Их нельзя назвать в ответе и нельзя найти по тексту |
| Планировщик: Pydantic-схема, категории и кухни как Enum, temperature 0, few-shot | Модель на 3B нестабильна на свободном тексте; схема и Enum ограничивают вывод, нулевая температура делает прогоны воспроизводимыми |
| Сырой ответ модели хранится рядом с проверенным | Чтобы разбирать ошибки: видно, что сказала модель и что осталось после проверки |
| Оценка без LLM | Эталон считает код по координатам; иначе судья мог бы ошибаться так же, как проверяемая система |
| RAG: префиксы `query:` и `passage:` у e5, русские названия кухонь в описании | Без префиксов e5 работает заметно хуже; без русских названий «грузинский» не связался бы с тегом `georgian`. Оба решения в пользу базовой линии |
| RAG получает k, равный размеру эталона; есть вариант «RAG + категория» | Не занижать базовую линию: разрыв должен быть оценкой снизу, а вклад расстояния отделён от ошибок категории |
| Дополнительный набор вопросов помечен как добавленный после результатов | Основную выборку не подгоняли под результат; сложные формулировки проверены отдельно |

## Ограничения

- **Выборка маленькая.** 19 основных и 8 дополнительных вопросов, доверительных интервалов нет; различия в десятых долях читать осторожно.
- **Планировщик на 3B-модели хрупкий.** На дополнительном наборе провалы: «Ближайший парк» (единственное число даёт `k=null`, система возвращает 5 мест вместо 1) и «Дворцовая пл.» (сокращение не распознано, ответа нет). Основные вопросы заданы с явным числом, а few-shot-примеры близки к ним по форме, поэтому 19 из 19 это работа на знакомых формулировках.
- **Эталон считается тем же `geo.py`**, что и использует геосистема. Расчёт расстояний проверен отдельно (`test_geo.py`: гаверсинус, парк-квадрат с точным ответом, перебор по кафе), но в оценке геосистема может ошибиться только на разборе вопроса.
- **Тип «по атрибуту» смещён в пользу тега.** Эталон строится по `cuisine`; RAG находит и места без тега, у которых название намекает на кухню, и это считается ошибкой. Его результат зависит от формулировки («японский ресторан» даёт 9 из 10, «Покажи японские рестораны» 0 из 17).
- **Данные OSM неполные.** Кухня указана у 46% мест, адрес у 8% (описания для RAG короткие). В данных есть дубли (два узла «Surf Coffee»).
- **Ориентиров 7.** «Невский проспект» это линия, в координатах одна точка, в вопросы на расстояние он не берётся. Вопросы без ориентира («Парк для прогулки в центре») система честно оставляет без ответа.
- Только три категории (`cafe`, `restaurant`, `park`); `fast_food`, `bar`, `pub` не включены. Ограничения адресов и времени работы в вопросах не поддерживаются.

## Что дальше

Это идеи, в работу не взяты:

- Научить планировщик единственному числу («ближайший» → `k=1`), сокращениям и вариантам названий; расширить список ориентиров геокодингом по любому названию.
- Усилить базовую линию (гибридный поиск по тексту и тегам, больше полей в описании) и честнее сравнить её по типу «по атрибуту».
- Расширить оценку: больше вопросов, независимая реализация эталона, доверительные интервалы.
- MCP-сервер для геоинструмента и упаковка в Docker.
- Эксперимент: несколько маленьких моделей голосуют за разбор вопроса против одной модели побольше (точность, время, токены).
- Автоматическое улучшение промпта планировщика по ошибкам из оценки.
